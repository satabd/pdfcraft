# Interface language

Choose **Menu > Edit > Preferences…** (Command-comma on macOS, Ctrl-comma elsewhere) **> Interface language** and select **Auto**, **English**, **日本語**, **简体中文**, **繁體中文**, **Čeština**, **Português (Brasil)**, **Deutsch**, **Español**, **Français**, **Русский**, **Қазақша**, **Български**, **తెలుగు**, **Magyar**, **Українська**, **Italiano**, **العربية**, **Polski**, **Slovenščina**, **Ελληνικά**, **Türkçe**, **Lietuvių** or **Tiếng Việt**. The change applies immediately and persists between launches. Command ids, document contents and file names are unchanged.

Displayed keyboard shortcuts use the same active interface language. For example, German shows `Strg+K` and `Strg+Umschalt+S` in the toolbar, menus, command palette, tooltips and Keyboard shortcuts dialog; macOS keeps its modifier symbols (`⌘`, `⇧`, `⌃`). Key names have their own `key` catalog context, so the Delete key can read `Entf` while the command remains `Löschen`. A missing key-name entry falls back to the English key name. Actual bindings and machine-facing command ids remain stable.

**Auto** (the default) follows the system language: `LC_ALL`, `LC_MESSAGES` or `LANG`, then the preferred-languages list on macOS. Any Portuguese locale (`pt_BR`, `pt_PT`) uses the Brazilian catalog, any French locale (`fr`, `fr_FR`, `fr_CA`, `fr_BE`) the French one, any German locale (`de`, `de_DE`, `de_AT`, `de_CH`) the German one, and Chinese locales for Taiwan, Hong Kong and Macau (`zh_TW`, `zh_HK`, `zh_MO`, `zh-Hant`) the Traditional Chinese one; other Chinese locales (`zh`, `zh_CN`, `zh_SG`, `zh-Hans`) the Simplified Chinese one. Telugu locales (`te`, `te_IN`) use the Telugu catalog, Bulgarian locales (`bg`, `bg_BG`) the Bulgarian one, and Hungarian locales (`hu`, `hu_HU`) the Hungarian one, and Ukrainian locales (`uk`, `uk_UA`) the Ukrainian one, and Italian locales (`it`, `it_IT`, `it_CH`) the Italian one, and Arabic locales (`ar`, `ar_MA`, `ar_EG`, `ar_SA`, …) the Arabic one, and Turkish locales (`tr`, `tr_TR`) the Turkish one, and Slovenian locales (`sl`, `sl_SI`) the Slovenian one, and Vietnamese locales (`vi`, `vi_VN`) the Vietnamese one. A system language without a catalog shows English. On Windows, **Auto** uses the Windows display languages, in preference order, when no supported locale is selected by those environment variables. Neutral `C`/`POSIX` locale values (including `C.UTF-8`) inherited from a launcher do not override the Windows display language; explicitly named supported locales such as `fr_FR.UTF-8` still do. The query asks Windows directly (`GetUserPreferredUILanguages`, through the `sys-locale` crate) without starting a process, and is cached for the process. If detection fails or the display language has no catalog, PdfCraft shows English.

The control channel exposes the setting through `ui.set`:

```json
{"method":"ui.set","params":{"key":"language","value":"ja"}}
```

The value is `auto` or a language code (`en`, `ja`, `zh-hans`, `zh-hant`, `cs`, `pt-br`, `de`, `es`, `fr`, `ru`, `kk`, `bg`, `te`, `hu`, `uk`, `it`, `ar`, `pl`, `sl`, `el`, `tr`, `lt` or `vi`), in any case. `ui.state` reports `language` as written in the preferences (`auto`, `en`, `ja`, `zh-hans`, `zh-hant`, `cs`, `pt-br`, `de`, `es`, `fr`, `ru`, `kk`, `bg`, `te`, `hu`, `uk`, `it`, `ar`, `pl`, `sl`, `el`, `tr`, `lt` or `vi`). Unknown values return an error without changing the current setting. Preferences saved before this setting existed follow the system language.

## Arabic and right-to-left text

The Arabic catalog has 2,137 entries in Modern Standard Arabic with Western digits. Counts use the six [CLDR Arabic forms](https://www.unicode.org/cldr/charts/48/supplemental/language_plural_rules.html#ar) (`0`, `1`, `2`, `3–10`, `11–99`, the rest), and dates use the Arabic names of the Gregorian months.

egui joins the letters of an Arabic word and runs them right to left, but it places the words of a line left to right in the order they are written. So catalog entries are written in logical (typing) order, and `i18n` puts each one into display order when the catalog loads (`bidi::display_rtl`): the line reads right to left, Latin words and numbers inside it read left to right, `{name}` placeholders and keyboard shortcuts stay whole, spaces at either end stay where the code concatenates, and a short caption keeps its colon on the right, beside the widget it captions. Lookups (`tl!`, `tr`, `trn`) therefore return display-order text for Arabic; `i18n::fmt` inserts values as they are. Text that egui wraps (tooltips, dialog text, preference notes) needs the logical text instead: `tl_logical!`, `i18n::tr_logical`, `fmt_logical` and `trn_logical` return it as an `i18n::Logical`, and `widgets::hover_text`, `body_text` and `styled_text` wrap it with the Unicode bidirectional algorithm (`bidi::wrap`) and set it against the right edge. Never pass `tl!` output to them: display-order text would be reordered twice. The toast and the notice bars above the pages take logical text too: `PdfCraftApp::notify` (and `notify_tr`, `notify_fmt`, which look the sentence up in the logical catalog) hold an `i18n::Logical`, and `widgets::logical_label` paints it, wrapped and right-aligned as wide as its longest line when it has right-to-left script, as an ordinary label otherwise; a document's name goes into the sentence through `fmt_logical`, which is how an Arabic name inside an English notice (or the other way round) reads in order. The command search matches a query of several Arabic words word by word.

Arabic in documents is a separate matter from the interface: Add text, Edit text, form fields (text, combo, list, comb cells and push-button captions), text-box comments (text box, callout, Typewriter, Fill & Sign text), a dynamic stamp's By line and measurement labels draw it shaped with the craft-fonts `Arab` face (`pdfcraft_fonts::shaped_text`), and a form field or text box with Arabic is right-aligned unless it states an alignment (`/Q`). Header & footer, Bates numbers and watermarks (`pdfcraft-edit`) and Create from text (`pdfcraft-create`, including generated comment summaries and compare reports) draw it shaped the same way, with the paragraph direction taken from its first strong character; without the face they refuse it (reports escape it as `[U+XXXX]`). Visible signatures (`pdfcraft-sign`) draw the signer's name, the reason, the location and the labels shaped too, one `/ActualText` span per line, a right-to-left line against the right edge of its column and the Latin and digits in place; without the face they are refused as before. The signing dialog still stamps its labels in English under the Arabic interface (its catalog is in display order), so Arabic labels come from `sign_document`'s `labels`. A dynamic XFA form's own text (draws, captions, read-only values) is drawn shaped too when the form is laid out (`pdfcraft-xfa`, so also in a flattened form or one converted to a static form): wrapped on shaped widths, one `/ActualText` span per line, right-aligned in a right-to-left paragraph unless the template states `hAlign`; without the face it is shown as `?` with a warning, as before. The Office exports (`pdfcraft-export`: Word, PowerPoint, HTML, RTF) are text writers, so Arabic and Hebrew need no face: the text is written as it is and each right-to-left paragraph is marked (`<w:bidi/>`, `rtl="1"`, `dir="rtl"`, `\rtlpar`). A table whose cells mostly open with a right-to-left letter (more than with a left-to-right one; a tie reads left to right) is mirrored as a whole: `<w:bidiVisual/>` in Word, `rtl="1"` on `<a:tblPr>` in PowerPoint, `dir="rtl"` on `<table>`, `\rtlrow` in RTF.

What Arabic does not have yet:

- **The layout is mirrored for the frame, not for everything in it.** In the Arabic interface the Tools pane is at the right of the document, the navigation panes (Bookmarks, Page thumbnails and the rest) at its left, and the rail at the left edge. That is the stock panel arrangement, laid out again when the language is switched (`Workspace::default_for`, `mirror_standard_shape`; the pane widths and which panes are open come along) and only if the arrangement has not been rearranged: a layout you moved, floated or tabbed stays as it is, and the explicit Tools panel side stays physical. The mode bar and the tab strip start at the right (menu and mode tabs, Home first; Open and the help, theme and Discord buttons at the left) while the window buttons stay where the desktop puts them. Rows start at the right in the All tools list and the tool pages, Bookmarks (indentation from the right, the destination page at the left), Fields, Layers, Attachments, the Pages panel header, the recent-files list, the command palette, and in dialog rows and in the footers that use `rtl::end` (OK and Cancel at the left); panel margins swap sides. Every caption-and-field form of the dialogs is laid out by `widgets::form_grid`: Document Properties, Rotate Pages, Number pages, Recover, Keyboard shortcuts, Set Page Boxes, Word Count, Recognize Text, Compare Files, Protect (advanced options), Print (printer, copies, paper and the driver's own options), Link, Field Properties (general, appearance, borders, position, text options, number and percent formats, add an action), Comment Properties, the redaction tool properties, Create Custom Stamp, the Action Wizard editor and the signing dialogs (new Digital ID, ID file, sign as, certificate details). The caption sits at the right of its field in a column as wide as the widest caption, with a short caption's colon moved to its left side, next to the field (in English the same call is an `egui::Grid`, unchanged: the accessibility tree and bounds of 30 English screens are identical to those before the change). A grid of colour swatches inside a field goes through `widgets::start_block`, which measures it in one frame and sets it against the right edge in the next. A form that stands beside other content (the page preview of Set Page Boxes, the two position columns of Field Properties) is given a width of its own, because a mirrored form fills the width it has. The menus, not only the main menu, put the label flush right and the shortcut at the left (`widgets::menu_entry`, `menu_icon_entry`, `menu_choice`, `sub_menu`): the main menu's File, Edit, Pages, View and Help, Display theme and Side panels submenus and the View menu's section labels, the tab context menu, the page, organize and Pages-panel menus, the comment, bookmark, accessibility, image and stamp menus, the Combine menus, the Comments panel's options and filter, the quick bar's popups and the tool flyouts (icon at the start, check mark at the end); the accessible name stays "label shortcut" and command ids and keyboard navigation are unchanged. Dialog titles (`widgets::dialog_title`) and the tab strips of Properties, About, Field Properties, Comment Properties, the Optimizer, Print's page handling and Shared Field Properties start at the right (`rtl::horizontal_wrapped`). The Optimizer's space table runs its columns right to left. A tool row, a tool-page entry and the search box that do not fit are cut in logical order (`widgets::paint_start`), so the ellipsis lands at the left of an Arabic sentence and its first words stay. Icons that point somewhere (`icons::MIRROR`: chevrons, undo and redo, panel and list glyphs) are flipped; the tab-scroll arrows and Move earlier or later keep their physical direction (`icons::image_fixed`). A submenu opens beside its entry on the side its arrow points to: to the left of it in Arabic, to the right of it in English, and to the other side where the window has no room (`widgets::sub_menu`, `rtl::submenu_align`; egui's `SubMenu` always prefers the right and has no setting for it, so `widgets/submenu.rs` is a copy of its open and close logic with the side chosen, and the command ids, hover delay and keyboard navigation are unchanged). The vertical scrollbar is at the left edge of the viewport in Arabic, in the Comments, Bookmarks, Pages, Fields, Layers, Attachments, Signatures and the other panes, the All tools list, the tool pages and stamp palette, the Organize and Measure panels, Preferences, the Home screen, the Combine grid, the Organize page grid (`widgets::scroll_area_with` around its `show_viewport`, as the document view), the scrolled lists and text boxes inside the dialogs and panels (the Document Properties and Keyboard Shortcuts lists, the link prompts, the choices popup of a list field, the digital-ID list of the signing dialog, the Shared Field Properties form, the JavaScript console and document script list, the measurement list, the tag tree, Prepare Form's item and field lists, the Search & Redact word list, the printer-driver options and the PDF/A report) and the scrolled menus: egui puts its bar at the right of every `ScrollArea` with no setting for the side, so `widgets::scroll_area` hides egui's bar and draws a thin floating one of its own from the area's reported geometry (widening on hover, a drag on the handle and a press in the track scroll the area), and is plain `ScrollArea::show` in English. The document view's vertical bar is at the left edge of the view as well: the canvas scroll area scrolls both ways (drag-scroll sources, wheel deferral, virtualized pages, zoom anchoring), none of which is touched, so it goes through the same code (`widgets::scroll_area_with` around its `show_viewport`), and because egui hides both bars with one setting the bottom bar is drawn by that code too, at the bottom edge where egui has it (`Axis::X`, the same handle, hover growth and dragging). The document tabs run from the start edge: under Arabic the first document is the rightmost tab and the next ones follow to its left (`rtl::run_order` draws the tabs left to right in reverse, the Combine tab at the far left), the strip starts scrolled to its right end (`stick_to_right`), the drop line and the drop position of a dragged tab read right to left (`drop_index`, `drop_marker`), and the arrows keep their physical sides (`Scroll tabs left` at the left of the tabs, `Scroll tabs right` at their right); the order of the documents, Ctrl+Tab and the tab menu are unchanged. The data tables that stay `egui::Grid`s run their columns right to left where they are tables of text: the Optimizer's space table, the contributor and model tables of About (the name column at the right, text right-aligned in slots as wide as the column's widest cell, the name column taking what the rest leaves; `credits::mirrored_table`), the calendar of a date field (Sunday is the rightmost column, and the arrows keep their places but the left one goes to the next month), and Shared Field Properties, which is a form of three cells (`widgets::form_grid_of`, `FormRows::row_with_note`): the apply checkbox that carries the property's name at the right, the editor to its left and the Mixed tag at the left of the editor. Mirroring changes positions only: catalog labels are already in display order and never go through `bidi::visual*` again. **Not mirrored:** the horizontal scrollbars of every area but the two that scroll both ways (the document view, `widgets::scroll_area_with`, and the About contributor and model tables, which draw their bottom bar the same way); the horizontal-only document tab strip and Combine file table keep egui's bar and the dock's own tab bars and drag handles; everything on the canvas (the page grid, its overlays such as the quick-action bar and the page-size badge, the Combine page and the Organize toolbar); the data tables that stay left-to-right `egui::Grid`s because they hold physical positions or a palette, not text: the header and footer boxes (the left, centre and right boxes are the page's left, centre and right, whatever the language of the interface), and the swatch grids (the colour palette in one fixed order, set against the start edge of a form by `widgets::start_block` but not reversed; the same grid in the comment properties and the shared field properties); the dialogs that were not given a form (the Preferences, header and footer, watermark and similar pages, whose rows are `rtl::horizontal` rows, with the colon of a short caption left at the right of the caption, away from the widget); and plain egui labels that a panel wraps. Dialog footers laid out with `Layout::right_to_left` directly rather than `rtl::end` (many of the dialogs above) keep OK and Cancel at the right.
- **Text you type into a field.** Single-line fields edit right-to-left script in display order. The fields made by `widgets::line` (search boxes, comment author and subject, the Comments panel's boxes, the text fields of the dialogs), the command palette, the bookmark search, Find in a document, the on-page form-field editor, the Fill & Sign text box and typed signature, the Tags panel's search and attribute values, the extract-pages file name and the Shared Field Properties tooltip are `widgets::BidiEdit`s: when the text holds right-to-left script the field draws it in display order and keeps egui's own `TextEdit`, so the caret, a click, a drag selection, Left and Right, undo and redo, the clipboard and an input method work on what is drawn, while what is stored, copied, announced and undone stays in typing order (`bidi::ScreenMap` relates the two orders; the galley is corrected to one glyph per character, because egui piles stray zero-width glyphs after every right-to-left word and gives a lam-alef ligature one glyph for its two letters). Typing Arabic after English puts each new letter to the left of the last with the caret staying where the next one appears; Backspace and Delete take the letter before and after the caret in typing order (Ctrl+Backspace and Ctrl+Delete a word); Home and End go to the start and end of a line that reads right to left (to the screen edges otherwise); Left and Right never stop twice inside a ligature. Fields still align to the script typed. A selection is the characters between two screen positions, so it is one highlighted stretch; where the text changes direction those characters are not contiguous in the stored text, and Copy, Cut and typing over it act on exactly the highlighted ones (Copy gives them in typing order). A single line reads in the direction of its first strong character, as `dir="auto"` has it and by the rule each paragraph of a multi-line field follows (`bidi::line_rtl`, `bidi::line_screen_map`): a line that starts in Arabic is laid out right to left (UAX #9 paragraph level 1), so an Arabic sentence followed by a Latin word draws the Latin word at its left end and the sentence's first word at the right, and the caret at the end of the text sits after that Latin word; a line that starts in Latin reads left to right as before; a line without a strong character (empty, or digits and punctuation only) takes the interface's direction, as the field's alignment does. The fields `widgets::line` makes, and the dialog fields above, sit against the right edge when their line reads right to left (`widgets::field_align`, the same first-strong rule); the Fill & Sign text box and the on-page form-field editor keep their left edge, where the text is placed on the page. **Multi-line fields** (`widgets::block`: the comment composer and the Comments panel's reply and edit boxes, the tag, figure-description, header-and-footer, watermark and computed-field boxes, the Search & Redact word list (one phrase per line, each read from its first strong letter), and the on-page editor of a multi-line form field) are `BidiEdit::multiline`s that do the same for paragraphs that wrap. When the text holds right-to-left script the field wraps each paragraph itself, at the width egui gives it (`bidi::wrapped_screen_map`: lines are measured in the field's font a word at a time, a word wider than a line breaks between characters, and the spaces after a word stay on its line so a space typed at the end shows), and hands egui the lines in display order, one galley row each. A typed Arabic paragraph therefore breaks between words in reading order, with its first words on the first row, where egui's own wrapping broke it at the wrong end. A paragraph's direction is that of its first strong character, as `dir="auto"`: right-to-left paragraphs are set against the right edge of the field and left-to-right ones against the left, in the same field; an empty or digits-only paragraph follows the one above it (the interface language for the first), so the new line after Enter stays on the side you were typing on. The breaks the wrapping makes are not characters of the text: the `ScreenMap` holds them as newlines of the screen text that map to no character (`bidi::VIRTUAL`), so the stored and announced text never gains a line break from a soft wrap, Backspace and Delete take the neighbouring character of the text across a wrap, and Copy, Cut and a selection across rows leave them out. Up and Down move between the rows as drawn, Home and End go to the left and right end of a row, Ctrl+Home and Ctrl+End to the start and end of the text in reading order, and Left and Right pass a wrap in one press, as they pass a newline. A caret at a wrap has two places on screen (the end of a row and the start of the next, or, in a right-to-left paragraph, the left end of one row and the right end of the next), and the field keeps which one you are at; resizing the field keeps the caret at the same place in the text. **The Add text box** (Edit a PDF ▸ Add content ▸ Text) is such a field too: typed Arabic and Hebrew read in display order, as in the saved text (words in reading order, the first word at the right), while the draft and the saved text stay in typing order. It passes `BidiEdit::layout` a hook (`LayoutCtx::layout_aligned`) that sets the rows of the box where the text's alignment puts them, as the page text is drawn (`edit/src/added.rs`): left, centre or right; a justified text with every row but the last stretched to the box's width by widening its spaces (`LayoutCtx::stretch_rows`: the glyphs after a space move on with it, so the caret and clicks stay on their letters; Latin and Arabic alike, as `added.rs` writes it), and the last row of a right-to-left paragraph at the right edge. The default alignment is left, so Arabic starts at the box's left edge in the box and on the page alike; choose Align right in the Format panel for a right-aligned Arabic box. (Latin text honours the alignment in the box now too.) Its lines break where the saved item's will, whichever text it holds: the field has no margin (its inner width is the saved box's, where the interface's own text box wrapped eight points narrower), wraps Latin text itself too (`BidiEdit::wrap_ltr`, so egui's wrapping by the interface font does not decide it), and measures a line with `pdfcraft_engine::AddedLineMeasure` (`edit/src/added.rs`, the widths `added_text_lines` wraps by: the standard font's for Latin, the craft-fonts face shaped word by word with the paragraph's space for a paragraph with Arabic or Hebrew), in points, so the breaks do not depend on the zoom and the width is compared to the digit (`BidiEdit::measure_in` with the paragraph the line is in, `wrap_at` the box's width, `wrap_key` the style; a word wider than the box stays whole and only the space ends a word, `bidi::WrapRules`, as the page writes it). The rows are drawn in the interface font with letter spacing that makes a row of Latin as wide as the page's line, at the page's line pitch (1.2 em), and a row a wrap ended is aligned without the space the break replaced, which the page does not write (`RowSlot::break_lead`, `break_trail`); Arabic and Hebrew rows are not letter-spaced (the interface's face is the page's). Kittests compare the rows of the box with the lines of the saved page (`text_lines`) for Latin, Arabic and Arabic mixed with Latin at two widths and three zooms, and the ink of each row with the page line's left and right ends at every alignment. Still different: Thai (the page breaks it between clusters, the box at spaces), the spaces a paragraph starts with show in the box and the page drops them, and italic and bold are not shown in the Latin rows (bold by the interface's semibold only). The field's layout is open to such hooks: `BidiEdit::layout` replaces the field's own galley (the hook gets the screen map and a `LayoutCtx` with the job, layout, glyph-alignment and row-placement steps, and runs for text without right-to-left script too, with the identity map), `wrap_at`, `measure_in` and `forced_rtl` replace the width lines break at, how a line is measured and the paragraphs' direction, and `show_mapped` returns the `ScreenMap` with `BidiOutput::logical_range`, the selection as a range of the stored text. **The Edit text box** (Edit a PDF ▸ Edit text & images, a click on a paragraph of the page) is a `BidiEdit::multiline` as well: Arabic and Hebrew in it read in display order (words in reading order, the first word at the right) while the draft, the applied edit and the page's `/ActualText` stay in typing order, and Latin text in it is laid out exactly as before. Its hook (`edit_text_ui::editor_galley`) is the editor's own layout, which draws every character in the font, size and colour of the page text it came from, run over the screen map's shaper text: each character of the display text takes the look of the stored character it was drawn from (`ScreenMap::shaper_source`; the line break the wrapping makes takes its neighbour's, and a look never changes inside a stretch of Arabic, which the text engine shapes as a whole). Arabic is drawn in the page's own face where Apply shapes the draft in it, and without the letter spacing that stretches the interface face to the width of the line it replaces. The engine decides which: `text_edit_layout` returns `shaping_faces`, the page font resource (per source line) whose complete face (static TrueType/OpenType that covers the draft; the block's own font or another resource of the same face on the page) the rewrite shapes each row in with its own tables, and the editor draws the joined letters of that line in the `pdf-source-N` family it installed for that font, so the rows are as wide as the page's. Where the rewrite draws Arabic as generated shaped glyphs instead (a subset or no embedded face, a font or weight change, a document font chosen, a letter the face lacks, a variable face it cannot embed) the editor keeps the interface's Arabic face (the bytes the page's shaper uses), as before. Retyped right-to-left text set in its own face now keeps the right edge of its rows, as the generated route does (the styled rewrite had set it left-aligned at the old rows' left edges); Hebrew keeps the page's font where it has the letters. The paragraph reads in the direction the page will write it (`forced_rtl(Some(pdfcraft_engine::rtl_base(draft)))`: more right-to-left letters than left-to-right ones; the first strong letter does not decide it, so an English word before most of an Arabic line leaves the line right to left), and a row that reads right to left sits against the right edge: of the page's own row while nothing has changed, of the paragraph's box after (the alignment chosen in the Format panel, if any: left, centre or right), as the engine right-aligns it; a line of such text that grows keeps its right edge and grows to the left. The editor wraps where the page will: not at all while the paragraph is as it was; once it has changed, the engine says where. The page's lines depend on the route the rewrite takes (a source font's metrics, a standard font's, the styled-region path with its per-character calibration, shaped Arabic with its own measure), none of which the interface can measure with its own fonts, so the overlay asks the rewrite itself: `pdfcraft_engine::TextDraftProbe::layout` runs `text_edit_layout` (the rewrite Apply runs, on a read-only copy of the document, the same call that already measures `draft_rect`; `text_edit_layout` now returns `rows`) and `BidiEdit::row_words` (with `wrap_ltr` for Latin) breaks the draft into those rows, keyed by the Format panel's values (`wrap_key`) so that changing the size rewraps the rows and keeps the selection. The rows the editor shows are therefore the page's after Apply for Latin text in a font the file does not embed (Inter against Helvetica broke them elsewhere) and for a multi-look Arabic block alike; a draft the rewrite refuses falls back to a measure of the editor's own (`edit_text_ui::line_measure`, through `BidiEdit::measure_in`), which sets each character of a line in the interface font and size of its own source row, by the looks the box draws by (`shaper_styles_of`, so a joined stretch takes its first letter's look and bold Arabic is measured at the face's bold instance), without the page's face or the Latin letter spacing; a paragraph of one look is measured as it always was, in its first row's font and size. The rewrite runs once more per change on the UI thread. The selection the Format panel formats is the characters between the caret's two ends, read from `BidiOutput::logical_range`. **Justify in the Edit text box.** A paragraph with Justify chosen in the Format panel is shown with the spaces of every row but the last stretched to the width of the row Apply will write (`TextEditLayout::row_rects`, the boxes of the rows the rewrite writes: `edit_text_ui::justify_like_the_page`), at every zoom, with the caret, clicks and selection on the letters they are over. The rewrite justifies on every route: the single-style one, the styled one (a paragraph of several looks, or a draft with explicit row breaks, which is every multi-row paragraph opened in the editor unless its breaks are deleted) and shaped Arabic in generated Type 3 glyphs. Each row the wrap breaks is stretched to the paragraph's width (`Tw` for a simple font; `TJ` adjustments after the spaces where word spacing does not reach: composite fonts, Type 3 codes, shaped glyphs); the last row of a paragraph, a row before a line break, a row of one word and a row that begins or ends with a space are not, and the editor shows those as the page writes them, unstretched (a right-to-left row keeps its right edge: a stretched one ends at the paragraph's, an unstretched one is right-aligned). **Several looks.** A paragraph of several looks (a larger first row, a bold or coloured word) keeps them when it is applied as it shows them in the box: the engine writes Arabic in the Arabic face with each character in the look of the stored character it came from and a joined word in its first letter's look, the rule the box draws by (`text_looks`, mirroring `shaper_styles`), and wraps each word in its own size. Bold Arabic (a bold run, a bold paragraph, a bold Add text item) is drawn on the page at the craft-fonts Arabic face's `wght` 700 instance, from Type 3 fonts of its own (a build whose face has no `wght` axis draws it regular). The Edit text and Add text boxes draw it at the same instance: their bold font is the `editor-bold` family (`theme::EDITOR_BOLD`), the interface's semibold faces with the Arabic face swapped for a copy whose `FontTweak` coordinates are `wght` 700, so a bold Arabic word is as wide in the box as on the page (بالعالم is 2.454 em regular and 2.760 em bold in both) and a justified row is stretched against glyphs of the page's width. Variation coordinates on a `TextFormat` would reach every variable face of the section's family (the craft-fonts Thai face is variable too, and so may an installed fallback be), so they are carried by that one face instead. The interface's own labels keep the semibold family, bold Latin is Inter SemiBold as before, and Hebrew, which no variable face draws, is unchanged. **Not covered by the Edit text box:** a row set in the interface's face (generated-glyph route) can differ in width from the page's by a few letters even though the breaks are the page's; the breaks are those of the previous text for one frame after a key press (the engine is asked for the new text in the next frame's layout), and fall back to the interface's measure where the rewrite refuses the draft; the first typed letter that makes a block read the other way is shown in the old direction for one frame, and a selection that crosses a change of direction formats the hull of its characters; the alignment chosen in the Format panel is shown for rows that read right to left only, apart from Justify (left-to-right rows keep the page's own left edge, or the centring a centred paragraph has); and the rows of a centred right-to-left title jump to the right edge once the text is edited, as the engine writes it. **Not covered by the field work:** fields of more than 50,000 characters (they stay egui's `TextEdit` in typing order, rather than stall a frame measuring lines), passwords and code editors (`widgets::plain_block`, the JavaScript editors) are untouched, and so are the fields for numbers and identifiers, which stay plain `TextEdit`s: the zoom and page-number boxes, the view filter, the page-range boxes and the date-format box. A multi-line field that gains right-to-left script while it is being typed in switches to this treatment on that keystroke, and back to egui's when the last such letter goes. Undo gives back the cursor it took with the text, which after a resize can lie in another wrapping: it is kept inside the text, not at the same letter, and the keys pressed in the same frame after an Undo wait for the next one. A line whose embeddings are nested to the limit of the bidirectional algorithm (about sixty unclosed ones) is drawn left to right instead of panicking in `unicode-bidi`. Tests that need an Arabic face skip in a build without craft-fonts; `PDFCRAFT_TEST_ARABIC_FONT=<font file>` stands one in for a local run.
- Labels built by joining translated pieces in code follow the reading order where they go through `rtl::join` (a list such as `A · B · C` is painted `C · B · A`, with `A` at the right) and `rtl::caption_value` (the value after its caption, "Issued by: …"): the digital-ID list, the Home cards and recent files, the Planned hint in the tools list, an attachment's details, the PDF/A issue line and the recovery list. A few lists are still joined left to right: the Combine page (which is not mirrored), the folder paths of Home's pinned folders, the font details in Properties and the structure tags.

These need bidirectional support in the text layout itself, not in the catalog.

Edit text (retyping existing text on a page) shapes Arabic with that face too: joined forms, marks and mixed Latin and digits, one `/ActualText` span per line so copy and search keep typing order (a line of several looks, such as a bold or larger word, a span per look, read back in typing order, so a second edit keeps the looks; a line whose spans would read out of order keeps one span and reads back in one look), and an error naming `CRAFT_FONTS_DIR` in a build without it (see [editing-existing-text.md](editing-existing-text.md)). Arabic glyphs come from the craft-fonts `Arab` face (Noto Sans Arabic, kept in the web build too). A build without craft-fonts shows Arabic as replacement boxes on the web; on desktop it falls back to one installed font (below). The craft-fonts revision pinned for CI and releases (`.github/workflows/`) has the Arabic face. That revision also holds Noto Sans CJK SC, which `crates/fonts/build.rs` never embeds: `AGENTS.md` §1.1 bars it, so Chinese still has no embedded face of its own (desktop builds fall back to an installed Chinese face, above).

File names and document titles in Arabic or Hebrew are drawn with a craft-fonts `Arab` face when the build input has one; on desktop, a character no embedded face has is drawn with one font already installed on the machine (`PDFCRAFT_SYSTEM_FONTS=0` turns this off). The tab strip, the recent-files list and Properties show such names in display order; Bookmarks, search results, Properties metadata, layer, attachment and field names, signature details, tags, form choices, Undo labels, notices and hover popups show document text in display order too (right-aligned where it wraps). Text you are typing is shown in display order in single-line fields (see above). Find ignores harakat and tatweel and matches presentation forms, the lam-alef ligature and Arabic-Indic or Persian digits; Search & Redact patterns read the page the same way (the pattern itself is matched against that folded text).

Japanese, Simplified Chinese, French, German and Brazilian Portuguese coverage tests, following PhotoCraft's complete-catalog approach, check every registered command, All tools label and `tl!("literal")` in the UI source. Simplified Chinese also checks direct `i18n::t` calls and multiline literals, plus the About tabs, contributor name modes, sort options, table headers and model columns. Generated history labels, contributor summaries and diagnostics are tested with user-supplied names and error details. Catalog coverage does not guarantee glyph coverage: the release-pinned craft-fonts input currently has no `Hans` face, and the web build embeds only BIZ UDPGothic Regular. Chinese font delivery remains separate work, as discussed in [#112](https://github.com/storytold/pdfcraft/pull/112) and [#140](https://github.com/storytold/pdfcraft/pull/140).

German labels keep nouns capitalized, including tool names inserted into notices. The certificate viewer uses the `certificate` context for `Subject` (the certificate holder), while document properties keep the plain translation (the topic). Search hints reserve room for the shortcut, and Home cards limit their title and description to the available rows; hovering shows the full text when it is shortened.

## How translations work

PdfCraft uses the same system as PhotoCraft (`crates/ui-egui/src/i18n/`):

- Strings in the code stay in English and serve as lookup keys. At draw time, `tl!("Save")` returns the text in the current language, and falls back to English when there is no entry.
- Each language has a catalog, `crates/ui-egui/src/i18n/<code>.tsv`, with one entry per line: `context<TAB>English<TAB>translation`. An empty context marks a plain string. `@id` keys an entry by command id (for example `file.saveAs`), so one menu item can read differently from another with the same English label. `@plural` holds plural forms. Any other context disambiguates an English word with several meanings (`tl_ctx!` in UI code, for example the signature pad's "Type" button against the "Type" column). The header of `ja.tsv` documents the format and escapes.
- Placeholders (`{name}`) must appear in both columns. A trailing `…` must be kept. `i18n::fmt` fills placeholders in one pass, so a value such as a file name containing `{n}` is inserted as written.
- Catalogs are validated strictly: unknown escapes, unknown `@` contexts, placeholder or ellipsis mismatches, wrong plural form counts and duplicates are errors. The tests require the bundled catalogs to have none; at run time a bad line is skipped (and logged) and that string shows in English.
- Catalogs are assets: each `.tsv` has an `ATTRIBUTION.toml` entry with `kind = "translation"` and its SHA-256, checked by `cargo xtask assets`. After editing a catalog, put the new hash into its entry by hand (`sha256sum crates/ui-egui/src/i18n/<code>.tsv`), because `cargo xtask assets --write` does not touch `ATTRIBUTION.toml`; the hash check is deliberate, so a changed asset gets its provenance re-checked. Without it `cargo xtask assets` and the test `assets::tests::the_real_manifest_passes` fail.
- Translations are clean-room: write them from the meaning of the English text, never from another product's string tables.

## Sentences the engine words

Some sentences are not the interface's own. The accessibility checker, the PDF/A verifier, the signature reader, the page-range parser and the edit history all word their own findings, and matching that wording in the UI with a `tl!` literal would break silently whenever the engine changed it. So those layers hand the wording over instead, apart from the document's own words:

- Each of them has a `WORDINGS` constant listing every sentence it can say, as `&'static str` with holes in it (`{n}`, `{p}`, `{}`). The sentence is written once, in the layer that means it.
- `said(&words)` says one of them: the layer looks its own wording up through the closure it is given, then fills the holes with the document's values — a page number, a font name, what the person typed — in one pass, so a value containing `{n}` is inserted as written.
- The UI passes `&crate::i18n::words`, which is a catalog lookup, so the sentence reads in the interface language. `in_english` is the same thing in English, and a wording with no entry comes back as it stands, which is the English — a catalog missing one shows an English sentence rather than a gap.
- The lists are `a11y::{WORDINGS, REPORT_WORDS}`, `preflight::WORDINGS`, `sign::pdf::{WORDINGS, kind::ALL}`, `print::WORDINGS` and the engine's `{EDIT_LABELS, BATCH_LABELS}`. `a11y::report_html` takes a language tag and a `words` closure, so a saved report reads the way the panel read, down to its `lang` attribute.
- `spanish_covers_what_the_engine_says` requires an entry for every wording in those lists, and `spanish_keeps_the_holes_in_what_the_engine_says` requires each translation to keep the same holes, so the catalog cannot fall behind the engine without a test saying so. Other languages are free to add the entries when they are translated; until then those sentences show in English as before.

Error details that come from the operating system, and faults rather than mistakes (a file that cannot be read, a lock that was poisoned), still carry their own text and are shown as they are.

## Adding a language

1. Copy the header of `ja.tsv` into `xx.tsv` and translate entries.
2. Add one row to `LANGUAGES` in `crates/ui-egui/src/i18n/mod.rs`: code, native name, catalog and plural rule.
3. Add an `ATTRIBUTION.toml` entry for the catalog (`kind = "translation"`), with the catalog's `sha256sum` as `sha256`, then run `cargo xtask assets --write` (it regenerates `ATTRIBUTION.md` only) and `cargo xtask assets`.

The Preferences dropdown, the system-language match and the catalog tests (format, duplicates, placeholders, plural forms, command ids) then pick it up.
