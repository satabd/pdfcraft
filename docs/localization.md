# Interface language

Choose **Menu > Edit > Preferences…** (Command-comma on macOS, Ctrl-comma elsewhere) **> Interface language** and select **Auto**, **English**, **日本語**, **简体中文**, **繁體中文**, **Čeština**, **Português (Brasil)**, **Deutsch**, **Español**, **Français**, **Русский**, **Қазақша**, **Български**, **తెలుగు**, **Magyar**, **Українська**, **Italiano**, **العربية**, **Polski**, **Slovenščina**, **Ελληνικά**, **Türkçe**, **Lietuvių** or **Tiếng Việt**. The change applies immediately and persists between launches. Command ids, document contents and file names are unchanged.

Displayed keyboard shortcuts use the same active interface language. For example, German shows `Strg+K` and `Strg+Umschalt+S` in the toolbar, menus, command palette, tooltips and Keyboard shortcuts dialog; macOS keeps its modifier symbols (`⌘`, `⇧`, `⌃`). Key names have their own `key` catalog context, so the Delete key can read `Entf` while the command remains `Löschen`. A missing key-name entry falls back to the English key name. Actual bindings and machine-facing command ids remain stable.

**Auto** (the default) follows the system language: `LC_ALL`, `LC_MESSAGES` or `LANG`, then the preferred-languages list on macOS. Any Portuguese locale (`pt_BR`, `pt_PT`) uses the Brazilian catalog, any French locale (`fr`, `fr_FR`, `fr_CA`, `fr_BE`) the French one, any German locale (`de`, `de_DE`, `de_AT`, `de_CH`) the German one, and Chinese locales for Taiwan, Hong Kong and Macau (`zh_TW`, `zh_HK`, `zh_MO`, `zh-Hant`) the Traditional Chinese one; other Chinese locales (`zh`, `zh_CN`, `zh_SG`, `zh-Hans`) the Simplified Chinese one. Telugu locales (`te`, `te_IN`) use the Telugu catalog, Bulgarian locales (`bg`, `bg_BG`) the Bulgarian one, and Hungarian locales (`hu`, `hu_HU`) the Hungarian one, and Ukrainian locales (`uk`, `uk_UA`) the Ukrainian one, and Italian locales (`it`, `it_IT`, `it_CH`) the Italian one, and Arabic locales (`ar`, `ar_MA`, `ar_EG`, `ar_SA`, …) the Arabic one, and Turkish locales (`tr`, `tr_TR`) the Turkish one, and Slovenian locales (`sl`, `sl_SI`) the Slovenian one, and Vietnamese locales (`vi`, `vi_VN`) the Vietnamese one. A system language without a catalog shows English. On Windows, **Auto** uses the Windows display languages, in preference order, when no supported locale is selected by those environment variables. Neutral `C`/`POSIX` locale values (including `C.UTF-8`) inherited from a launcher do not override the Windows display language; explicitly named supported locales such as `fr_FR.UTF-8` still do. The query asks Windows directly (`GetUserPreferredUILanguages`, through the `sys-locale` crate) without starting a process, and is cached for the process. If detection fails or the display language has no catalog, PdfCraft shows English.

The control channel exposes the setting through `ui.set`:

```json
{"method":"ui.set","params":{"key":"language","value":"ja"}}
```

The value is `auto` or a language code (`en`, `ja`, `zh-hans`, `zh-hant`, `cs`, `pt-br`, `de`, `es`, `fr`, `ru`, `kk`, `bg`, `te`, `hu`, `uk`, `it`, `ar`, `pl`, `sl`, `el`, `tr`, `lt` or `vi`), in any case. `ui.state` reports `language` as written in the preferences (`auto`, `en`, `ja`, `zh-hans`, `zh-hant`, `cs`, `pt-br`, `de`, `es`, `fr`, `ru`, `kk`, `bg`, `te`, `hu`, `uk`, `it`, `ar`, `pl`, `sl`, `el`, `tr`, `lt` or `vi`). Unknown values return an error without changing the current setting. Preferences saved before this setting existed follow the system language.

## Arabic and right-to-left text

The Arabic catalog has 2,137 entries in Modern Standard Arabic with Western digits. Counts use the six [CLDR Arabic forms](https://www.unicode.org/cldr/charts/48/supplemental/language_plural_rules.html#ar) (`0`, `1`, `2`, `3–10`, `11–99`, the rest), and dates use the Arabic names of the Gregorian months.

egui joins the letters of an Arabic word and runs them right to left, but it places the words of a line left to right in the order they are written. So catalog entries are written in logical (typing) order, and `i18n` puts each one into display order when the catalog loads (`bidi::display_rtl`): the line reads right to left, Latin words and numbers inside it read left to right, `{name}` placeholders and keyboard shortcuts stay whole, spaces at either end stay where the code concatenates, and a short caption keeps its colon on the right, beside the widget it captions. Lookups (`tl!`, `tr`, `trn`) therefore return display-order text for Arabic; `i18n::fmt` inserts values as they are. Text that egui wraps (tooltips, dialog text, preference notes) needs the logical text instead: `tl_logical!`, `i18n::tr_logical`, `fmt_logical` and `trn_logical` return it as an `i18n::Logical`, and `widgets::hover_text`, `body_text` and `styled_text` wrap it with the Unicode bidirectional algorithm (`bidi::wrap`) and set it against the right edge. Never pass `tl!` output to them: display-order text would be reordered twice. The toast and the notice bars above the pages take logical text too: `PdfCraftApp::notify` (and `notify_tr`, `notify_fmt`, which look the sentence up in the logical catalog) hold an `i18n::Logical`, and `widgets::logical_label` paints it, wrapped and right-aligned as wide as its longest line when it has right-to-left script, as an ordinary label otherwise; a document's name goes into the sentence through `fmt_logical`, which is how an Arabic name inside an English notice (or the other way round) reads in order. The command search matches a query of several Arabic words word by word.

Arabic in documents is a separate matter from the interface: Add text, Edit text, form fields (text, combo, list, comb cells and push-button captions), text-box comments (text box, callout, Typewriter, Fill & Sign text), a dynamic stamp's By line and measurement labels draw it shaped with the craft-fonts `Arab` face (`pdfcraft_fonts::shaped_text`), and a form field or text box with Arabic is right-aligned unless it states an alignment (`/Q`). Header & footer, Bates numbers and watermarks (`pdfcraft-edit`) and Create from text (`pdfcraft-create`, including generated comment summaries and compare reports) draw it shaped the same way, with the paragraph direction taken from its first strong character; without the face they refuse it (reports escape it as `[U+XXXX]`). Visible signatures (`pdfcraft-sign`) draw the signer's name, the reason, the location and the labels shaped too, one `/ActualText` span per line, a right-to-left line against the right edge of its column and the Latin and digits in place; without the face they are refused as before. The signing dialog still stamps its labels in English under the Arabic interface (its catalog is in display order), so Arabic labels come from `sign_document`'s `labels`. A dynamic XFA form's own text (draws, captions, read-only values) is drawn shaped too when the form is laid out (`pdfcraft-xfa`, so also in a flattened form or one converted to a static form): wrapped on shaped widths, one `/ActualText` span per line, right-aligned in a right-to-left paragraph unless the template states `hAlign`; without the face it is shown as `?` with a warning, as before. The Office exports (`pdfcraft-export`: Word, PowerPoint, HTML, RTF) are text writers, so Arabic and Hebrew need no face: the text is written as it is and each right-to-left paragraph is marked (`<w:bidi/>`, `rtl="1"`, `dir="rtl"`, `\rtlpar`).

What Arabic does not have yet:

- **The layout is mirrored for the frame, not for everything in it.** In the Arabic interface the Tools pane is at the right of the document, the navigation panes (Bookmarks, Page thumbnails and the rest) at its left, and the rail at the left edge. That is the stock panel arrangement, laid out again when the language is switched (`Workspace::default_for`, `mirror_standard_shape`; the pane widths and which panes are open come along) and only if the arrangement has not been rearranged: a layout you moved, floated or tabbed stays as it is, and the explicit Tools panel side stays physical. The mode bar and the tab strip start at the right (menu and mode tabs, Home first; Open and the help, theme and Discord buttons at the left) while the window buttons stay where the desktop puts them. Rows start at the right in the All tools list and the tool pages, Bookmarks (indentation from the right, the destination page at the left), Fields, Layers, Attachments, the Pages panel header, the recent-files list, the command palette, and in dialog rows and in the footers that use `rtl::end` (OK and Cancel at the left); panel margins swap sides. Every caption-and-field form of the dialogs is laid out by `widgets::form_grid`: Document Properties, Rotate Pages, Number pages, Recover, Keyboard shortcuts, Set Page Boxes, Word Count, Recognize Text, Compare Files, Protect (advanced options), Print (printer, copies, paper and the driver's own options), Link, Field Properties (general, appearance, borders, position, text options, number and percent formats, add an action), Comment Properties, the redaction tool properties, Create Custom Stamp, the Action Wizard editor and the signing dialogs (new Digital ID, ID file, sign as, certificate details). The caption sits at the right of its field in a column as wide as the widest caption, with a short caption's colon moved to its left side, next to the field (in English the same call is an `egui::Grid`, unchanged: the accessibility tree and bounds of 30 English screens are identical to those before the change). A grid of colour swatches inside a field goes through `widgets::start_block`, which measures it in one frame and sets it against the right edge in the next. A form that stands beside other content (the page preview of Set Page Boxes, the two position columns of Field Properties) is given a width of its own, because a mirrored form fills the width it has. The menus, not only the main menu, put the label flush right and the shortcut at the left (`widgets::menu_entry`, `menu_icon_entry`, `menu_choice`, `sub_menu`): the main menu's File, Edit, Pages, View and Help, Display theme and Side panels submenus and the View menu's section labels, the tab context menu, the page, organize and Pages-panel menus, the comment, bookmark, accessibility, image and stamp menus, the Combine menus, the Comments panel's options and filter, the quick bar's popups and the tool flyouts (icon at the start, check mark at the end); the accessible name stays "label shortcut" and command ids and keyboard navigation are unchanged. Dialog titles (`widgets::dialog_title`) and the tab strips of Properties, About, Field Properties, Comment Properties, the Optimizer, Print's page handling and Shared Field Properties start at the right (`rtl::horizontal_wrapped`). The Optimizer's space table runs its columns right to left. A tool row, a tool-page entry and the search box that do not fit are cut in logical order (`widgets::paint_start`), so the ellipsis lands at the left of an Arabic sentence and its first words stay. Icons that point somewhere (`icons::MIRROR`: chevrons, undo and redo, panel and list glyphs) are flipped; the tab-scroll arrows and Move earlier or later keep their physical direction (`icons::image_fixed`). A submenu opens beside its entry on the side its arrow points to: to the left of it in Arabic, to the right of it in English, and to the other side where the window has no room (`widgets::sub_menu`, `rtl::submenu_align`; egui's `SubMenu` always prefers the right and has no setting for it, so `widgets/submenu.rs` is a copy of its open and close logic with the side chosen, and the command ids, hover delay and keyboard navigation are unchanged). The vertical scrollbar is at the left edge of the viewport in Arabic, in the Comments, Bookmarks, Pages, Fields, Layers, Attachments, Signatures and the other panes, the All tools list, the tool pages and stamp palette, the Organize and Measure panels, Preferences and the scrolled menus: egui puts its bar at the right of every `ScrollArea` with no setting for the side, so `widgets::scroll_area` hides egui's bar and draws a thin floating one of its own from the area's reported geometry (widening on hover, a drag on the handle and a press in the track scroll the area), and is plain `ScrollArea::show` in English. Mirroring changes positions only: catalog labels are already in display order and never go through `bidi::visual*` again. **Not mirrored:** the scrollbars of the scroll areas that were not converted (the document view, Home, the lists inside dialogs and Combine keep egui's bar at the right, as do all horizontal bars) and the dock's own tab bars and drag handles; the order of the document tabs (the first tab is the leftmost); everything on the canvas (the page grid, overlays, the Combine page and the Organize toolbar); the data tables that stay left-to-right `egui::Grid`s because they are wide tables of numbers, names or physical positions, not forms (the header and footer boxes, whose left, centre and right are the page's; Shared Field Properties, with its apply checkboxes; the contributor and model tables of About; the calendar of a date field; the swatch grid itself); the dialogs that were not given a form (the Preferences, header and footer, watermark and similar pages, whose rows are `rtl::horizontal` rows, with the colon of a short caption left at the right of the caption, away from the widget); and plain egui labels that a panel wraps. Dialog footers laid out with `Layout::right_to_left` directly rather than `rtl::end` (many of the dialogs above) keep OK and Cancel at the right.
- **Text you type into a field.** Single-line fields edit right-to-left script in display order. The fields made by `widgets::line` (search boxes, comment author and subject, the Comments panel's boxes, the text fields of the dialogs), the command palette, the bookmark search, Find in a document and the on-page form-field editor are `widgets::BidiEdit`s: when the text holds right-to-left script the field draws it as `bidi::visual` does and keeps egui's own `TextEdit`, so the caret, a click, a drag selection, Left and Right, undo and redo, the clipboard and an input method work on what is drawn, while what is stored, copied, announced and undone stays in typing order (`bidi::ScreenMap` relates the two orders; the galley is corrected to one glyph per character, because egui piles stray zero-width glyphs after every right-to-left word and gives a lam-alef ligature one glyph for its two letters). Typing Arabic after English puts each new letter to the left of the last with the caret staying where the next one appears; Backspace and Delete take the letter before and after the caret in typing order (Ctrl+Backspace and Ctrl+Delete a word); Home and End go to the start and end of text that begins in a right-to-left script (to the screen edges otherwise); Left and Right never stop twice inside a ligature. Fields still align to the script typed. A selection is the characters between two screen positions, so it is one highlighted stretch; where the text changes direction those characters are not contiguous in the stored text, and Copy, Cut and typing over it act on exactly the highlighted ones (Copy gives them in typing order). A field's base direction is left to right, as in `bidi::visual`: an Arabic sentence followed by a Latin word draws the Latin word at its right. **Multi-line fields** (`widgets::block`: the comment composer and the Comments panel's reply and edit boxes, the tag, figure-description, header-and-footer, watermark and computed-field boxes, and the on-page editor of a multi-line form field) are `BidiEdit::multiline`s that do the same for paragraphs that wrap. When the text holds right-to-left script the field wraps each paragraph itself, at the width egui gives it (`bidi::wrapped_screen_map`: lines are measured in the field's font a word at a time, a word wider than a line breaks between characters, and the spaces after a word stay on its line so a space typed at the end shows), and hands egui the lines in display order, one galley row each. A typed Arabic paragraph therefore breaks between words in reading order, with its first words on the first row, where egui's own wrapping broke it at the wrong end. A paragraph's direction is that of its first strong character, as `dir="auto"`: right-to-left paragraphs are set against the right edge of the field and left-to-right ones against the left, in the same field; an empty or digits-only paragraph follows the one above it (the interface language for the first), so the new line after Enter stays on the side you were typing on. The breaks the wrapping makes are not characters of the text: the `ScreenMap` holds them as newlines of the screen text that map to no character (`bidi::VIRTUAL`), so the stored and announced text never gains a line break from a soft wrap, Backspace and Delete take the neighbouring character of the text across a wrap, and Copy, Cut and a selection across rows leave them out. Up and Down move between the rows as drawn, Home and End go to the left and right end of a row, Ctrl+Home and Ctrl+End to the start and end of the text in reading order, and Left and Right pass a wrap in one press, as they pass a newline. A caret at a wrap has two places on screen (the end of a row and the start of the next, or, in a right-to-left paragraph, the left end of one row and the right end of the next), and the field keeps which one you are at; resizing the field keeps the caret at the same place in the text. **The Add text box** (Edit a PDF ▸ Add content ▸ Text) is such a field too: typed Arabic and Hebrew read in display order, as in the saved text (words in reading order, the first word at the right), while the draft and the saved text stay in typing order. It passes `BidiEdit::layout` a hook (`LayoutCtx::layout_aligned`) that sets the rows of the box where the text's alignment puts them, as the page text is drawn (`edit/src/added.rs`): left, centre or right; a justified text at the left, except the last row of a right-to-left paragraph, which ends at the right edge. The default alignment is left, so Arabic starts at the box's left edge in the box and on the page alike; choose Align right in the Format panel for a right-aligned Arabic box. (Latin text honours the alignment in the box now too.) The field's layout is open to such hooks: `BidiEdit::layout` replaces the field's own galley (the hook gets the screen map and a `LayoutCtx` with the job, layout, glyph-alignment and row-placement steps, and runs for text without right-to-left script too, with the identity map), `wrap_at`, `measure` and `forced_rtl` replace the width lines break at, how a line is measured and the paragraphs' direction, and `show_mapped` returns the `ScreenMap` with `BidiOutput::logical_range`, the selection as a range of the stored text. **Not covered:** the Edit text box (existing page text) is still left to right and its rows follow the source's left edge: typed words run left to right while editing, and what is stored is correct; a single line's base direction is still left to right; fields of more than 50,000 characters (they stay egui's `TextEdit` in typing order, rather than stall a frame measuring lines), passwords and code editors (`widgets::plain_block`) are untouched, and so is the Edit text box (below), the Search & Redact word list, the zoom and page boxes and a few other fields (tag search, the extract-name box, Fill & Sign text). A multi-line field that gains right-to-left script while it is being typed in switches to this treatment on that keystroke, and back to egui's when the last such letter goes. Undo gives back the cursor it took with the text, which after a resize can lie in another wrapping: it is kept inside the text, not at the same letter, and the keys pressed in the same frame after an Undo wait for the next one. A line whose embeddings are nested to the limit of the bidirectional algorithm (about sixty unclosed ones) is drawn left to right instead of panicking in `unicode-bidi`. Tests that need an Arabic face skip in a build without craft-fonts; `PDFCRAFT_TEST_ARABIC_FONT=<font file>` stands one in for a local run.
- Labels built by joining translated pieces in code follow the reading order where they go through `rtl::join` (a list such as `A · B · C` is painted `C · B · A`, with `A` at the right) and `rtl::caption_value` (the value after its caption, "Issued by: …"): the digital-ID list, the Home cards and recent files, the Planned hint in the tools list, an attachment's details, the PDF/A issue line and the recovery list. A few lists are still joined left to right: the Combine page (which is not mirrored), the folder paths of Home's pinned folders, the font details in Properties and the structure tags.

These need bidirectional support in the text layout itself, not in the catalog.

Edit text (retyping existing text on a page) shapes Arabic with that face too: joined forms, marks and mixed Latin and digits, one `/ActualText` span per line so copy and search keep typing order, and an error naming `CRAFT_FONTS_DIR` in a build without it (see [editing-existing-text.md](editing-existing-text.md)). Arabic glyphs come from the craft-fonts `Arab` face (Noto Sans Arabic, kept in the web build too). A build without craft-fonts shows Arabic as replacement boxes on the web; on desktop it falls back to one installed font (below). The craft-fonts revision pinned for CI and releases (`.github/workflows/`) has the Arabic face. That revision also holds Noto Sans CJK SC, which `crates/fonts/build.rs` never embeds: `AGENTS.md` §1.1 bars it, so Chinese still has no embedded face of its own (desktop builds fall back to an installed Chinese face, above).

File names and document titles in Arabic or Hebrew are drawn with a craft-fonts `Arab` face when the build input has one; on desktop, a character no embedded face has is drawn with one font already installed on the machine (`PDFCRAFT_SYSTEM_FONTS=0` turns this off). The tab strip, the recent-files list and Properties show such names in display order; Bookmarks, search results, Properties metadata, layer, attachment and field names, signature details, tags, form choices, Undo labels, notices and hover popups show document text in display order too (right-aligned where it wraps). Text you are typing is shown in display order in single-line fields (see above). Find ignores harakat and tatweel and matches presentation forms, the lam-alef ligature and Arabic-Indic or Persian digits; Search & Redact patterns read the page the same way (the pattern itself is matched against that folded text).

Japanese, Simplified Chinese, French, German and Brazilian Portuguese coverage tests, following PhotoCraft's complete-catalog approach, check every registered command, All tools label and `tl!("literal")` in the UI source. Simplified Chinese also checks direct `i18n::t` calls and multiline literals, plus the About tabs, contributor name modes, sort options, table headers and model columns. Generated history labels, contributor summaries and diagnostics are tested with user-supplied names and error details. Catalog coverage does not guarantee glyph coverage: the release-pinned craft-fonts input currently has no `Hans` face, and the web build embeds only BIZ UDPGothic Regular. Chinese font delivery remains separate work, as discussed in [#112](https://github.com/storytold/pdfcraft/pull/112) and [#140](https://github.com/storytold/pdfcraft/pull/140).

German labels keep nouns capitalized, including tool names inserted into notices. The certificate viewer uses the `certificate` context for `Subject` (the certificate holder), while document properties keep the plain translation (the topic). Search hints reserve room for the shortcut, and Home cards limit their title and description to the available rows; hovering shows the full text when it is shortened.

## How translations work

PdfCraft uses the same system as PhotoCraft (`crates/ui-egui/src/i18n/`):

- Strings in the code stay in English and serve as lookup keys. At draw time, `tl!("Save")` returns the text in the current language, and falls back to English when there is no entry.
- Each language has a catalog, `crates/ui-egui/src/i18n/<code>.tsv`, with one entry per line: `context<TAB>English<TAB>translation`. An empty context marks a plain string. `@id` keys an entry by command id (for example `file.saveAs`), so one menu item can read differently from another with the same English label. `@plural` holds plural forms. Any other context disambiguates an English word with several meanings (`tl_ctx!` in UI code, for example the signature pad's "Type" button against the "Type" column). The header of `ja.tsv` documents the format and escapes.
- Placeholders (`{name}`) must appear in both columns. A trailing `…` must be kept. `i18n::fmt` fills placeholders in one pass, so a value such as a file name containing `{n}` is inserted as written.
- Catalogs are validated strictly: unknown escapes, unknown `@` contexts, placeholder or ellipsis mismatches, wrong plural form counts and duplicates are errors. The tests require the bundled catalogs to have none; at run time a bad line is skipped (and logged) and that string shows in English.
- Catalogs are assets: each `.tsv` has an `ATTRIBUTION.toml` entry with `kind = "translation"` and its SHA-256, checked by `cargo xtask assets`. After editing a catalog, put the new hash into its entry by hand (`sha256sum crates/ui-egui/src/i18n/<code>.tsv`), because `cargo xtask assets --write` does not touch `ATTRIBUTION.toml`; the hash check is deliberate, so a changed asset gets its provenance re-checked. Without it `cargo xtask assets` and the test `assets::tests::the_real_manifest_passes` fail.
- Translations are clean-room: write them from the meaning of the English text, never from another product's string tables.

## Sentences the engine words

Some sentences are not the interface's own. The accessibility checker, the PDF/A verifier, the signature reader, the page-range parser and the edit history all word their own findings, and matching that wording in the UI with a `tl!` literal would break silently whenever the engine changed it. So those layers hand the wording over instead, apart from the document's own words:

- Each of them has a `WORDINGS` constant listing every sentence it can say, as `&'static str` with holes in it (`{n}`, `{p}`, `{}`). The sentence is written once, in the layer that means it.
- `said(&words)` says one of them: the layer looks its own wording up through the closure it is given, then fills the holes with the document's values — a page number, a font name, what the person typed — in one pass, so a value containing `{n}` is inserted as written.
- The UI passes `&crate::i18n::words`, which is a catalog lookup, so the sentence reads in the interface language. `in_english` is the same thing in English, and a wording with no entry comes back as it stands, which is the English — a catalog missing one shows an English sentence rather than a gap.
- The lists are `a11y::{WORDINGS, REPORT_WORDS}`, `preflight::WORDINGS`, `sign::pdf::{WORDINGS, kind::ALL}`, `print::WORDINGS` and the engine's `{EDIT_LABELS, BATCH_LABELS}`. `a11y::report_html` takes a language tag and a `words` closure, so a saved report reads the way the panel read, down to its `lang` attribute.
- `spanish_covers_what_the_engine_says` requires an entry for every wording in those lists, and `spanish_keeps_the_holes_in_what_the_engine_says` requires each translation to keep the same holes, so the catalog cannot fall behind the engine without a test saying so. Other languages are free to add the entries when they are translated; until then those sentences show in English as before.

Error details that come from the operating system, and faults rather than mistakes (a file that cannot be read, a lock that was poisoned), still carry their own text and are shown as they are.

## Adding a language

1. Copy the header of `ja.tsv` into `xx.tsv` and translate entries.
2. Add one row to `LANGUAGES` in `crates/ui-egui/src/i18n/mod.rs`: code, native name, catalog and plural rule.
3. Add an `ATTRIBUTION.toml` entry for the catalog (`kind = "translation"`), with the catalog's `sha256sum` as `sha256`, then run `cargo xtask assets --write` (it regenerates `ATTRIBUTION.md` only) and `cargo xtask assets`.

The Preferences dropdown, the system-language match and the catalog tests (format, duplicates, placeholders, plural forms, command ids) then pick it up.
